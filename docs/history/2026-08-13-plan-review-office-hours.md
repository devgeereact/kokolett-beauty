## Problem Statement

`docs/plan.md` — "2026 Owner-First Full Product Upgrade" — proposes 24 steps
across 7 phases (baseline audit → 7-nav IA collapse → workflow contracts per
nav → new Reports/AI Assistant/Email Ops modules → data-integrity hardening
→ 2026 design-system modernization → reliability/QA/release governance) for
a single-owner, single-location hair salon's booking and ops platform. The
question on the table: is this worth building as scoped, what's the riskiest
assumption in it, what should be cut or resequenced, and what's the fastest
way to know if the Phase 1 nav bet is right before committing to the other
six phases.

## Reality Check — the finding that reframes the whole question

Before touching premises: **most of what this plan asks for has already
shipped**, and it shipped by a different mechanism than the plan describes.

Direct evidence, read from this repo, not inferred:

- `docs/history/2026-08-13-baseline-audit.md` and `docs/history/2026-08-13-capability-matrix.md` — Phase 0, Tasks
  1–2 — exist on disk, dated 2026-08-13, and are thorough (they cite
  file:line evidence for every claim).
- `git log --oneline` shows Phase 1's core move already merged: `5012def
Restructure owner dashboard nav to 7-nav model, surface orphaned pages`
  and `52a25dc Consolidate Approvals and Requests into a tabbed Inbox` —
  both committed **after** the baseline audit, which itself documents the
  _old_ 9-entry nav as the then-current state. The plan's own before/after
  is visible in two consecutive git states in the same repo.
- Reading `src/components/dashboard/DashboardLayout.tsx` right now confirms
  the live primary nav is exactly the plan's 7 items — Today, Inbox,
  Calendar & Capacity, Bookings, Customers, Growth, Settings — with Reports
  and AI Assistant kept reachable as secondary entries rather than hidden,
  which is a _better_ resolution of Phase 1 Step 7 ("temporarily remove or
  relabel dead-nav entries") than the plan itself proposed, because it turns
  out those aren't dead — they're real, working modules.
- Phase 3's "missing production modules" (Reports, AI Assistant) are not
  missing. `85f199a Build the AI Assistant: 8 advisory modules, wired to
real data` and `3d8a11f Build the Reports page` both predate the Phase 0
  baseline audit itself — they were built _before_ the plan's own
  dependency chain says Phase 3 is unlocked (`_depends on Phase 2_`, which
  depends on Phase 1, which depends on Phase 0).
- Phase 2's cross-nav quick actions (Step 9) and blocking-dialog removal
  (Step 10) are also already shipped: `75b1dbf Add the cross-nav
quick-action launcher (Cmd+K)`, `8f3d71c Replace blocking
window.confirm/alert with ConfirmDialog/Toast in the owner dashboard`.
- The two specs cited for cross-reference (`2026-08-13-today-command-center…`
  and `docs/history/2026-08-14-calendar-rebuild-design.md`) are exactly Phase 5's "2026
  design-system modernization" and part of Phase 1/2's workflow redesign —
  but neither document cites a plan.md phase or step number anywhere. They
  were each generated from a direct owner ask ("rebrand Today," "make the
  calendar feel like Apple Calendar"), scoped tightly, shipped same-day or
  next-day.

**What this means:** the actual operating model on this project is not
"Phase 0 unlocks Phase 1 unlocks Phase 2…" — it's "owner names a concrete
want → a design spec is written and reviewed → an implementation plan is
written → it ships," running in parallel, out of the plan's own declared
order, and faster than the plan's dependency graph would allow if followed
literally. `docs/plan.md`'s phase-gating language ("blocks all other
phases," "_depends on Phase 0_") describes a waterfall that the project has
already, correctly, ignored in practice.

This is the single most important fact for answering "is this plan worth
building as scoped": **as a literal, ordered, dependency-gated 24-step
backlog, no — because it's already stale as a backlog on day one, and the
project is visibly succeeding by not following it that way.** As a loose
menu of ideas to pull individual items from when they bite, several of its
remaining items (below) are worth keeping.

## Premises

1. Phase 0 and the core of Phase 1 (7-nav IA, Inbox consolidation, orphaned
   pages surfaced) are already implemented and live in the current
   codebase. **Agree** — direct git/file evidence above, not disputable.
2. The plan's declared "Primary KPI: reduce owner daily time spent" has no
   cited baseline. Nowhere in `docs/plan.md`, `docs/PRD.md`, or the two
   audits is there a number for how long the owner currently spends on
   admin, before or after the nav change. It is asserted, not measured.
   **Agree** — confirmed by grep; no timing data exists anywhere in the
   docs tree.
3. This is an n=1 product on the dashboard side — one owner, one login,
   forever (per `docs/PRD.md` §3, §6: "The owner authenticates through
   Supabase Auth… and is the only account that can mutate salon data").
   Phase 4's contract-level RPC guards and Phase 6's release-wave/UAT/
   ops-dashboard ceremony are patterns built for a team shipping to many
   users and many stakeholders coordinating a release. **Agree** — this is
   architecturally true per `docs/ARCHITECTURE.md` §8 and `docs/PRD.md` §3,
   not a matter of interpretation.
4. `docs/RULES.md` already mandates `typecheck` + `lint` (zero warnings) +
   CodeRabbit review on every PR (§7, confirmed: `"strict": true`, `npm run
typecheck`/`lint` in `package.json`). Plan Step 24's "Quality gates
   before each release wave: typecheck, lint, test suite, UAT sign-off" is
   substantially already standing practice, not a new phase to build.
   **Agree.**
5. Every phase in the plan (1 through 6) is owner-console-facing. None of
   the six phases touches booking conversion, marketing, or demand — the
   PRD's own stated problem #1 ("customers abandon booking when it requires
   an account" — already solved by passwordless identity) and #3 ("empty
   slots stay empty") get no dedicated phase; Growth-nav gets one plan
   sentence ("manage website-facing offer/requests/subscribers/reviews")
   and nothing else. **Agree**, and this is the scope-imbalance premise
   the plan doesn't name explicitly.

**[JUDGMENT CALL]** All five premises above are "agreed" because I am
standing in for the founder in a non-interactive run. A live owner might
push back on #5 in particular — she may have already decided (correctly,
for her business) that admin-time relief is genuinely the highest-leverage
lever right now, e.g. because booking volume is fine and time is the actual
constraint on taking more of it. Nothing in the docs proves or disproves
this either way; it's the one premise a real conversation would resolve in
five minutes and this session cannot.

## The Riskiest Assumption

Not the 7-nav bet — that one is already resolved by production reality (see
below). The plan's actual riskiest assumption is quieter and sits underneath
everything from Phase 2 onward:

> **That dashboard/ops efficiency is the highest-leverage problem for this
> business right now, encoded as "reduce owner daily time spent" — with zero
> measured baseline to confirm it, and zero phase dedicated to the PRD's own
> other two stated money-losers (booking abandonment, empty slots staying
> empty).**

This is a classic "solution in search of validated demand" pattern in
miniature: the plan is thorough and well-evidenced about _what exists in
the code_, and almost entirely silent on _what the owner's actual day
costs her right now_, which is the only number that would tell you whether
Phase 4–6's remaining ~15 steps are worth six more weeks versus, say, one
week fixing the two concrete revenue-adjacent gaps the capability matrix
already found (Growth's orphaned `AppointmentTypePage`/`WeeklyDefaultPage` —
an owner who can't find the screen that sets her own price and capacity is
losing more than admin minutes).

Second-order risk, more tactical: the plan treats "validating" a nav change
as if this were a multi-user product needing a phased rollout and formal
UAT (Phase 6, Step 23: "structured UAT by owner task journeys"). With n=1,
there is no sampling problem and no need for a rollout wave — the fastest,
cheapest, most direct signal is a five-minute conversation with the one
person who uses it, which the plan doesn't schedule anywhere before Phase 6.

## What To Cut Or Resequence

**Cut outright** (disproportionate to a one-owner business, or already
covered by existing practice):

- Step 22 — dedicated production ops dashboards/alerts for email queue
  health, realtime subscription health, error trends. Sentry is already the
  monitoring stack (`docs/ARCHITECTURE.md` topology diagram, `src/lib/
sentry.ts`). Building a second observability surface for one operator to
  check is process theatre; extend Sentry alerting/dashboards instead of
  standing up a new module.
- Step 24's four-wave phased release choreography (Wave A/B/C/D). There is
  one production environment and one deploy path (`docs/DEPLOYMENT.md`);
  the project's actual release cadence is already same-day spec→plan→ship.
  Formal waves add coordination overhead with nobody to coordinate with.
- Step 2's formal "capability matrix" as a recurring artifact per phase.
  Valuable once, as Phase 0 proved — expensive to maintain as ongoing
  ceremony when the codebase moves this fast; it will be stale again within
  days, as it already was for the nav model by the time this review ran.

**Keep, but resequence ahead of everything else** — these are concrete
correctness bugs the audits already found, not process:

- Booking management's reschedule split-brain: Today's inline reschedule
  calls `create_appointment_as_owner` (creates a duplicate, leaves the
  original dangling) while every other reschedule path calls
  `reschedule_appointment_as_owner` (atomic retire-and-recreate).
  `docs/history/2026-08-13-capability-matrix.md` §1 and §3 both flag this independently. This
  is real data-integrity risk (Phase 4's actual point) and it's small,
  scoped, and already fully diagnosed — a day of work, not a phase.
- `AppointmentTypePage` (price/duration) and `WeeklyDefaultPage` (weekly
  capacity) are fully built, real screens with zero inbound links from any
  nav — per the capability matrix, "an owner cannot change her price, her
  appointment length, or her weekly hours pattern without already knowing a
  URL exists." Confirm whether `5012def`'s "surface orphaned pages" already
  closed this (the commit message claims it did); if so, mark it done and
  move on — if not, this is the single highest-value fix left in the plan.

**Keep, unchanged in shape, because they're already working exactly as
scoped**: the spec-driven pattern demonstrated by the Today/payment-log spec
and the Calendar rebuild spec. Don't replace this with the plan's phase
structure — extend it. Phase 5 ("2026 design-system modernization") is
_already happening_, one page at a time, through exactly this mechanism.

## Fastest Way To Validate The Phase 1 Nav Bet

The honest answer is that this question is largely moot — the bet is
already placed and live. But the fastest way to get a real signal, cheaper
than anything Phase 6 proposes:

1. **Ask her directly, this week.** N=1, no sampling problem: "Can you find
   things faster now?" is a five-minute conversation, not a UAT script.
2. **Watch one real day, don't help** (this is Phase 2A's own Q5 pattern,
   applied here instead of skipped because the plan was pre-formed). Sit
   behind her for the messiest hour of a real shift and note what she
   reaches for and hesitates on. That's worth more than the formal "task
   journeys" in Step 23.
3. **Check the two orphaned-page fixes specifically** — verify she can now
   find `AppointmentTypePage` and `WeeklyDefaultPage` since `5012def`
   claims to have surfaced them. This is the one piece of Phase 1 the
   capability matrix flagged as still possibly broken, and it's a two-
   minute check, not a phase.

No dashboard, no alerting, no phased rollout is needed to answer this
question for one user who is reachable by walking over and asking.

## Approaches Considered

### Approach A: Follow `docs/plan.md` literally as written

Continue Phases 4–6 exactly as scoped: contract-level RPC guards across all
write paths, new ops-dashboard module, formal phased release waves A–D,
structured UAT scripts, recurring capability-matrix audits.

- Effort: XL (human: several weeks / CC: several days of agent time across
  many sessions)
- Risk: Medium — not a correctness risk, a _process_ risk: it slows the
  demonstrably faster spec→plan→ship loop already working, and duplicates
  effort (a fresh capability matrix will be stale again within days, as
  this one already is for the nav).
- Pros: thorough; would genuinely harden a multi-tenant, multi-stakeholder
  product.
- Cons: solo-owner business with no second stakeholder to coordinate
  release waves with; several "missing module" premises are already false.

### Approach B: Cut hard, fold survivors into the existing spec-driven loop (recommended)

Retire `docs/plan.md`'s phase-gate structure as a literal backlog. Pull the
concrete, still-real items (reschedule split-brain bug, orphaned-page
discoverability check, any genuinely missing Phase 4 guard) into the same
mechanism already producing results: owner names a want or a bug surfaces →
`/office-hours` or `/design-consultation` gut-checks it → a scoped spec →
an implementation plan → ship, one slice at a time. Keep `docs/RULES.md`'s
existing typecheck/lint/CodeRabbit gate as the only "release governance"
this team size needs.

- Effort: S, ongoing (human: an afternoon to re-triage the plan's remaining
  items / CC: minutes per item as they come up)
- Risk: Low — this is formalizing a pattern already proven to work twice
  (Today spec, Calendar spec), not introducing a new one.
- Pros: matches actual team size and demonstrated velocity; each shipped
  slice is independently valuable instead of gated behind phase dependency
  chains; avoids the "stale on day one" problem the audit evidence shows
  the current plan already has.
- Cons: loses the single-document narrative of "here's the whole 2026
  upgrade" — a reader wanting one plan.md to point at for the full arc
  won't have it. Mitigated by keeping a short, living punch-list instead
  of a phased plan.

### Approach C: Split the plan into two tracks — "bug fixes" and "growth," drop "ops governance" entirely

Same spirit as B, but explicit about the scope-imbalance premise (#5
above): open a second, thin track for the PRD's under-served money-losers
(booking-abandonment, empty-slot visibility) alongside the bug-fix track,
and drop Phase 6's release-governance content as a category rather than
resequencing it.

- Effort: M (human: needs the owner to weigh in on whether growth is
  actually the constraint / CC: same as B for execution once scoped)
- Risk: Low-Medium — the risk is entirely in premise #5's judgment call;
  if she confirms admin time genuinely is the bottleneck, this track adds
  scope she didn't ask for.
- Pros: directly answers the riskiest-assumption finding above instead of
  leaving it unresolved.
- Cons: requires the one conversation this non-interactive session
  couldn't have — whether time or revenue is the real constraint.

## Recommended Approach

**Approach B**, with Approach C's growth-track question flagged as the
first thing to resolve in the assignment below — not because it's wrong to
ask, but because asking it live costs five minutes and shouldn't gate
shipping the bug fixes B already identifies as ready now.
